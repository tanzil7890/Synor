This page covers the full picture of failure behavior in Synor — from how components fail in isolation, through what happens during interrupted updates, to the APIs for observing and reacting to errors in production.

For a quick overview of failure isolation and the two-phase model, see [What happens when a component fails](../programming_guide/processing_component#what-happens-when-a-component-fails) in the Processing Component guide.

## The guiding principle

**Scheduling background work is non-blocking; observing its readiness is truthful.** Starting a component returns a handle immediately. Waiting for that handle, or for the enclosing app operation, never turns failed work into success.

| API | What it takes to return | Raises on failure? |
|---|---|---|
| `syn.spawn`, `syn.spawn_each`, `LiveComponentOperator.update`/`.delete` | the work is *scheduled* (returns a handle) | **No** — execution runs in the background |
| `await handle.ready()` (any of the above) | reaches *ready state* | **Yes** — only durable success resolves normally |
| `await LiveComponentOperator.update_full()` | reaches *ready state* of the full cycle | **Yes** — same shape as `handle.ready()` |
| `await syn.call(...)` | the inner component's *value* is produced | **Yes** — component success is on the critical path |
| `await app.drop()` (and `synor drop`) | GC succeeds at *every* level | **Yes**, at any depth — leaking target state would otherwise go silent |

The parent aggregates descendant readiness, so a failed background child also fails the enclosing app update even when user code never awaits that child's handle. Sibling components continue independently, allowing all useful work and error reporting to finish before the operation returns its terminal result.

`syn.auto_refresh` is an explicit retry policy: its first cycle must succeed before readiness, while a later cycle reports and raises internally, then the wrapper catches that terminal result and proceeds to the next scheduled cycle.

## Reporting versus propagation

Exception handlers report failures to logs, metrics, alerting, or incident systems. They do not decide whether work succeeded. Returning normally marks the failure as reported; raising delegates reporting to the next outer handler. In both cases, `handle.ready()`, `update_full()`, and the enclosing app operation retain the original terminal failure.

[Live components](./live_component) follow the same principle: their `update`/`delete`/`update_full` calls route failures through this chain with `mount_kind="process_live"`. The operator also exposes [`report_exception(exc)`](./live_component#report_exception) for surfacing errors raised in `process_live`'s body that aren't already routed by `update`/`delete`/`update_full`.

## Processing and submit phases

Synor processes each component in two phases:

1. **Processing** — runs your function, declares target states in memory. This phase is side-effect-free. If it fails (e.g., a parsing error, an API timeout), no writes were attempted.
2. **Submit** — writes changes to target backends. This phase only runs after processing completes successfully.

This separation means a processing failure never leaves partial data in your targets.

## Interrupted updates and recovery

An update can be interrupted by various events: a process kill (SIGKILL), Ctrl+C (SIGINT), an unhandled exception, or a target backend failure during submit.

**What state is left behind?**

Synor's internal database (LMDB) uses transactions, so its own state is always consistent even after a crash. Synor tracks all possible states a target could be in — if an update is interrupted partway through a commit, both the old and new states are retained as possibilities. This ensures no state is ever lost.

**Recovery is automatic.** On the next `app.update()`, Synor computes the current desired state and reconciles against all possible previous states. The target connector converges the target to the correct state regardless of whether the previous commit partially succeeded or never ran.

For details on how target handlers deal with multiple possible previous states after an interruption, see [Custom Target Connector — Handle multiple previous states](./custom_target_connector#handle-multiple-previous-states).

## Monitoring errors

`app.update()` returns an `UpdateHandle` that exposes processing stats, including error counts:

```python
handle = app.update()

# Poll stats at any time
stats = handle.stats()
if stats is not None:
    print(f"Errors: {stats.total.num_errored}")

# Stream progress
async for snapshot in handle.watch():
    print(f"{snapshot.stats.total.num_errored} errors so far")
```

See [Progress monitoring](./progress_monitoring) for the full `UpdateHandle` API.

## Exception handlers

For background-mounted components (`spawn()` and `spawn_each()`), you can register **exception handlers** to observe or react to failures — for example, to send alerts, record metrics, or implement custom logic.

Synor supports two levels of exception handlers:

- **Global (environment-level)**: registered once in your lifespan function; applies to all background mounts in the environment.
- **Scoped**: an async context manager that applies to all `spawn()` / `spawn_each()` calls made within it.

:::note
Exception handlers only apply to `spawn()` and `spawn_each()`. `call()` propagates errors directly to the caller since the parent has an explicit dependency on the result.
:::

### Global exception handler

Register a handler inside your `@syn.lifespan` function using `builder.set_exception_handler()`:

```python
import synor as syn

@syn.lifespan
def lifespan(builder: syn.EnvironmentBuilder):
    def on_error(exc: BaseException, ctx: syn.ExceptionContext) -> None:
        print(f"[{ctx.env_name}] {ctx.mount_kind} failed at {ctx.stable_path}: {exc}")

    builder.set_exception_handler(on_error)
    yield
```

This replaces the default error log with your reporting behavior for all background mounts in the environment. It does not suppress readiness propagation.

### Scoped exception handler

Use `syn.exception_handler()` as an async context manager to apply a handler to a specific dynamic scope:

```python
@syn.task
async def process_all(files):
    def on_error(exc: BaseException, ctx: syn.ExceptionContext) -> None:
        print(f"Failed processing {ctx.stable_path}: {exc}")

    async with syn.exception_handler(on_error):
        for f in files:
            await syn.spawn(syn.unit_path(str(f.path)), process_file, f)
```

The handler applies to all `spawn()` / `spawn_each()` calls within the `async with` block, including those in nested functions called from within the block.

### Handler type

Both sync and async handlers are supported:

```python
from typing import Awaitable

# Sync handler
def sync_handler(exc: BaseException, ctx: syn.ExceptionContext) -> None:
    ...

# Async handler
async def async_handler(exc: BaseException, ctx: syn.ExceptionContext) -> None:
    await send_alert(exc, ctx)
```

The type alias is:

```python
ExceptionHandler = Callable[
    [BaseException, ExceptionContext],
    None | Awaitable[None],
]
```

### `ExceptionContext` fields

Your handler receives an `ExceptionContext` dataclass with information about the failure:

| Field | Type | Description |
|---|---|---|
| `env_name` | `str` | Name of the Synor environment |
| `stable_path` | `str` | Full stable path of the failing component |
| `processor_name` | `str \| None` | Name of the processor (best-effort) |
| `mount_kind` | `"mount" \| "mount_each" \| "delete_background" \| "process_live"` | Source of the failure: `"mount"`/`"mount_each"` for background build errors, `"delete_background"` for sweep-driven deletions, `"process_live"` for exceptions surfaced from a live component's `process_live` via `LiveComponentOperator.report_exception` (e.g. a failed `syn.auto_refresh` cycle) |
| `parent_stable_path` | `str \| None` | Stable path of the parent component |
| `is_background` | `bool` | Always `True` for exception handler invocations |
| `source` | `"component" \| "handler"` | `"component"` for the original failure; `"handler"` if a handler itself raised |
| `original_exception` | `BaseException \| None` | The original component exception, set only when `source == "handler"` |

### Handler stacking and fallback

Handlers are stacked: the most specific (innermost) handler runs first.

If the innermost handler raises an exception, the next outer handler is called with that new exception. In this case `ctx.source` is `"handler"` and `ctx.original_exception` holds the original component error.

This continues up the stack. If all handlers raise, Synor logs the reporting failure separately. If no handler is registered, Synor logs the component failure at `ERROR`. Either way, the original component failure remains the readiness result.

```python
@syn.lifespan
def lifespan(builder: syn.EnvironmentBuilder):
    builder.settings.db_path = "..."

    def global_handler(exc: BaseException, ctx: syn.ExceptionContext) -> None:
        if ctx.source == "handler":
            # A handler itself failed — exc is the handler's exception,
            # ctx.original_exception is the original component error.
            print(f"Handler error: {exc}; original: {ctx.original_exception}")
        else:
            print(f"Component error: {exc}")

    builder.set_exception_handler(global_handler)
    yield

@syn.task
async def _root() -> None:
    def inner_handler(exc: BaseException, ctx: syn.ExceptionContext) -> None:
        print(f"inner: {exc}")
        raise RuntimeError("inner handler failed")  # falls through to global_handler

    async with syn.exception_handler(inner_handler):
        await syn.spawn(syn.unit_path("child"), _child)
```

Users who never register handlers get the default `ERROR` log. Siblings continue independently, while the failed handle and enclosing operation still raise.
